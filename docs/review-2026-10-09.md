## 已修复问题

### 1. JSON 数值先舍入，后续校验失去原始信息

当前 toolchain 的 core JSON 对普通有限小数只保留 Double。
`1.0000000000000001` 可变成 `1`，`1e-999` 可变成 `0`；因此仅检查
Double 是否等于转换后的整数并不够。受影响位置包括资源编号、协议版本、配置
版本、trace 元数据和交付证据；通用 API 重序列化也可能改变响应中的数值。

现在通过 `internal/wire_json` 复用 `moonbitstack/moonjson@0.4.0` 的严格解析，
保留数字原文。项目只实现协议所需的有界非负整数校验：拒绝被舍入的小数和
非零下溢，同时保留 `1`、`1.0`、`10e-1` 等等价整数表示。
发布验证器对机器生成的版本、退出码和文件大小进一步要求规范整数写法。

数字、数组和对象仍使用 core 的 `Json`，DTO 的 FromJson/ToJson 和输出结构
本轮复检保持原接口；当时解析深度为 1024，重复成员保持最后值，未启用 JSON5 语法。
后续 Windows 托管 CI 在深层嵌套测试中出现栈溢出，因此将各平台深度预算统一收紧到
128，并补充边界接受与超深拒绝测试；最新平台证据见 [ci.md](ci.md)。
SDK 消费者若先用其他有损解析器构造 Json，已丢失的数字原文无法由 DTO 恢复；
严格校验保证覆盖本项目直接处理的 HTTP、配置、trace 和证据文本入口。

### 2. 分页在聚合后才校验资源，导致无效请求和错误归属丢失

原实现先收集多页 Json，最后转换 DTO。首屏出现非法资源状态时，仍可能请求
第二页；多页聚合失败后也无法确定错误属于哪个响应。

现在 `Client::read_list[T]` 在每一页进入聚合结果前解码，坏页立即停止。
失败仍不返回部分结果，并保留出错页的 HTTP 状态与安全 request ID。
首屏坏数据和第二屏坏数据都有回归覆盖；后者同时验证已成功取得的第一页不会
泄露为成功结果。页数、条数、重试预算和单页 continuation 契约保持不变。

### 3. trace 替换后的路径可能超过自身读取限制

原路径在替换前符合 2048 字符上限，重复出现的短 token 被替换为 `[redacted]`
后却可能超过上限，甚至使写出的 JSONL 超过 reader 的单行限制。

现在每次替换后检查长度，超过限制则把整条路径归为 `[redacted]`。
回归验证生成的记录仍能被本项目 trace reader 读取，不记录原始秘密或正文。

### 4. 发布验证器未完整检查“完成”证据

除了上述数值问题，原验证器没有要求完整的模块、平台、工具链、依赖与源码
元数据，也没有确认必要交付文件及 runner/checks 一致性。

现在要求必要元数据和文件存在，checks 包含可执行程序及参数，并与已完成的
runner-status 一致。`1e-999` 冒充成功退出码的问题在旧验证器上实际复现，
新回归还覆盖舍入后的版本/场景数、缺失元数据、清单与 runner 不一致，以及
同时删除必需文件和对应清单条目。普通哈希仍仅证明一致性，不证明发行者身份。

### 5. 候选内的活动模块文件会被开发工具识别

本轮首次候选生成后，验证器发现额外的 `.mooncakes` 和 `_build`，正确拒绝。
这些文件在清单完成前已出现；本机存在运行中的 MoonBit LSP，但本轮未独立
追踪具体写入进程，因此不把工具归因写成已证实事实。

交付只需要元数据快照，故将 `moon.mod` 打包为 `moon.mod.txt`，避免把候选
呈现为待构建的嵌套项目；runner 也在完成前检查未列入清单的文件。
验证器兼容旧版候选的 `moon.mod` 名称，仍拒绝额外文件。新候选及其搬迁副本
使用随包验证器成功通过，不在交付目录内生成缓存。

## 优化与复用取舍

- 共享 `internal/wire_json` 的解析策略和整数规则，避免各个数值入口单独修补。
- 将单资源读取与分页列表读取分开，删除 `list` 模式分支及聚合 Json 后再次遍历
  的路径；共用失败结果构造逻辑。
- 删除分页 visited 集合：Link 校验已经要求同一路由、相同 page size、严格
  `page + 1`，且页码有上限，集合不能再识别额外的循环。
- CLI 的 read/mutation/api 共用 trace warning 合成，保持 stdout/stderr 和退出码。
- 保留 typed read 重试、mutation 单次发送、generic API 单次发送的独立策略；
  不为语法相似而混淆不同的副作用边界。
- 保留 standalone `.mbtx` 脚本中的少量独立封装，使随包验证器可搬迁执行，
  不为消除少量重复额外引入构建框架。

新增依赖的选择依据：
[moonjson 0.4.0](https://mooncakes.io/docs/moonbitstack/moonjson) 返回 core Json，
保留数字文本且支持严格 JSON。已安装版本源码和实际回归验证了所需行为。
已安装的 x/json5 使用 Double 且接受更宽语法；x/decimal 不接受科学计数法，
小数 scale 上限为 28，均不适合替代这个输入边界。项目没有另写通用 JSON parser。
依赖固定在 moon.mod，Apache-2.0 文本随候选携带，见 third-party-notices.md。

## 仍开放的边界

- 真实 MoonHub `/api/v1`、Bearer 生命周期、授权过滤、原子 ETag、异步合并与
  pipeline 行为仍需服务端实现和联调，fixture 不能替代这些证据。
- Linux/Windows Native 运行、真实 HTTPS 信任链及无效证书拒绝、平台权限/ACL、
  并发锁和取消语义的完整平台验收仍以 release.md 为准。
- 仓库仍没有 HEAD 提交；清单如实记录 revision=null、dirty/untracked。此次
  没有提交、推送或发布，也不把本地候选称为可重现的正式发行版。
- 不宣称性能提升、完整 GitHub gh 兼容或“再无缺陷”；本报告结论限于上述
  源码复核、可执行回归和指定宿主的实际证据。
